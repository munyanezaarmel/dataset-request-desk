# NOTES

## 1. Design

**Data model.** Five PostgreSQL tables: `users` (role: client/operator/admin), `episodes`,
`requests`, `request_status_history` (who/when/from/to for every change) and `assignments`.
All state lives in the database; the API is stateless apart from the JWT. Migrations are managed
with Alembic, and the tests build the test database from those migrations.

**Hardest decisions**
1. *"An episode belongs to at most one request."* I made `assignments.episode_pk` the primary key,
   so the database itself refuses a second assignment, even if two operators click at the same
   moment. The code also checks first, for friendly error messages, and locks the request row
   (`SELECT ... FOR UPDATE`) so "deliver" cannot interleave with "assign". A test with two
   threads proves exactly one wins.
2. *CSV import policy.* Cleanable differences (case, spaces, day-first dates) are normalised;
   values that could be wrong (negative or huge duration, unknown robot, invalid quality) are
   skipped and reported, not guessed. Re-importing is safe because of `ON CONFLICT DO NOTHING`,
   and an existing episode is never overwritten.
3. *Where the status rules live.* One dictionary `(from, to) -> allowed roles` plus one function.
   Order of errors: move does not exist = 409, wrong role = 403, business rule = 409.
   Clients asking for another client's request get 404, so ids cannot be probed.

Other decisions: median is first `submitted` to first `delivered` (rework does not distort it);
analytics days are UTC and the range is inclusive; assignments only change while a request is
`in_progress` and are kept when a delivery is rejected.

## 2. Left out or simplified, and next steps

**Stretch item: deployment (Render).** The app runs as two Docker web services plus a managed
PostgreSQL database, defined in `render.yaml`, with HTTPS provided by Render. Secrets are not in the
repository: `JWT_SECRET` is generated by Render and `DATABASE_URL` is injected from the managed
database. Migrations run automatically on start. It is a demo environment: free services sleep when
idle (an external uptime monitor pings both services every 5 minutes during the review period) and
the free database expires after 30 days.

Left out: no refresh tokens, no login rate limiting, no user-admin screen (API only), no pagination
controls in the UI, no browser (end-to-end) tests. CI runs the backend tests on every push.

With two more days: move the JWT to an httpOnly cookie, rate-limit login, stream the CSV import
with `COPY`, add a daily summary table for analytics, and add end-to-end tests.

## 3. Something that went wrong

**Alembic could not generate the first migration.** `alembic revision --autogenerate` failed with
`NoSuchModuleError: Can't load plugin: sqlalchemy.dialects:driver`.

*Diagnosis.* `driver://user:pass@localhost/dbname` is Alembic's placeholder database URL, so the
error meant my `env.py` change (which sets the real URL from the app settings) was not being used.
The file looked correct in my editor, so I checked what the container actually read:
`grep -c set_main_option /app/alembic/env.py` returned 0 inside the container. I confirmed the volume
mount in `docker-compose.yml` was configured, recreated the container, and compared the file on my
machine with the one in the container. The edit was visible in my editor but had not been saved to
disk, so the container kept reading Alembic's original `env.py`. After saving the file, the migration
generated and applied correctly.

*Lesson.* When a tool's behaviour contradicts the code I can see, I first check what the process
actually reads (the file inside the container) before changing code. I now keep checks like that as
one-line commands.

## 4. Security

- **Passwords:** hashed with bcrypt (per-user salt); login always runs one bcrypt check so timing
  does not reveal which emails exist. Seed passwords exist in plain text only in the dev seed file.
  The public demo is seeded with those same development accounts, so its data is disposable; a real
  deployment would create accounts with strong, private passwords.
- **Tokens:** signed JWT (HS256), 60 minutes. The user is loaded from the database on every
  request, so deactivating a user takes effect immediately.
- **Validation:** Pydantic schemas on every input plus CHECK/UNIQUE constraints in the database.
  SQL is parameterised by SQLAlchemy. Authorization is enforced on the server; the UI only hides buttons.
- **Two vulnerabilities I worry about most:**
  1. The token sits in `localStorage`, so any script injected into the page could steal it, and
     tokens cannot be revoked before they expire. Fix: httpOnly cookie, short-lived access
     tokens with refresh rotation.
  2. No rate limiting on `/auth/login`, so passwords can be brute-forced. Fix: per-IP and
     per-account limits and lockout. (Also: the dev secrets in docker-compose must come from a
     secret store in production.)

## 5. Scale

- **10x users:** the first limits are bcrypt CPU on login and the per-process connection pool.
  Run several API workers behind a load balancer and size the pool. The per-request user lookup
  could be cached briefly. Row locks only conflict on the same request, so they scale fine.
- **100x episodes:** analytics scans grow. Add `(recorded_at, robot_id)`, a daily summary table
  and monthly partitions. The episode list's `count(*)` and OFFSET paging get slow; use keyset
  paging. The importer holds valid rows in memory; use streaming and `COPY` into a staging table.
- **Hosting:** the free tier suspends idle services (cold starts of 1-2 minutes) and its database
  expires after 30 days. A real deployment would use always-on instances and a managed database
  with backups.
